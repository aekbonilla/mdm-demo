What Is MDM?

Mobile Device Management is a policy enforcement layer between an organization and the devices its users carry.


Core capabilities:

  • Remote lock & wipe
  • Enforce encryption & passcode
  • App allow/block lists
  • VPN & Wi-Fi profile push
  • Certificate management
  • Compliance monitoring

Tools we use today:


Android Headwind MDM
Open-source · Docker · localhost:8080


iOS NanoMDM
Open-source · Docker · localhost:9000


Attack mitmproxy
Network interception · localhost:8082

MDM protocol on iOS is Apple's proprietary APNs-based protocol. Android uses its own Device Policy Manager API. Both are standardised — Headwind and NanoMDM implement the open specs.

Demo 1 — Android Policy Enforcement Android

ATTACK: Employee device has no MDM — weak PIN, USB debugging on, sideloading enabled. Any physical attacker or malicious app can exploit this.
DEFENCE: Push a policy from Headwind MDM admin panel.

Live in Headwind MDM (localhost:8080):

  • Configurations → New → Set min passcode length = 8
  • Screen lock timeout = 30 s
  • Disable camera, disable USB debug
  • Assign to mdm_demo device → Save
  • Watch emulator receive the policy
# Verify via ADB
./android/adb-demo.sh info
Open the browser to localhost:8080. Login admin/hmdm. Go to Configurations, create a new config, set the fields listed above. Assign to the enrolled device. Save. Switch to emulator window — show settings changed. Then run: ./android/adb-demo.sh info

Demo 2 — MITM / Rogue AP Attack Android

ATTACK:
Route emulator through mitmproxy.
Simulates user connecting to a rogue WiFi hotspot.
# Route traffic through attacker
./android/adb-demo.sh mitm

# Watch intercepted traffic:
open http://localhost:8082
DEFENCE:
MDM enforces always-on VPN.
Clear the proxy — encrypted tunnel takes over.
# Simulate VPN enforcement
./android/adb-demo.sh vpn

mitmproxy intercepts plaintext HTTP. With always-on VPN enforced by MDM, the device cannot connect without tunnelling — the proxy sees only encrypted noise.

Run mitm command first. Open a browser on the emulator and navigate to any http:// site. Switch to mitmproxy web UI (localhost:8082) — show request details, headers, cookies. Then run the vpn command and show that mitmproxy no longer sees cleartext. Point out: in production, MDM pushes the VPN profile automatically on enrollment.

Demo 3 — Remote Lock & Wipe Android

SCENARIO: Employee reports their device stolen. It contains corporate email, VPN credentials, and customer data.
RESPONSE (seconds, not hours):

Via Headwind MDM panel:

  • Devices → select device
  • Lock Device → instant
  • Send Message → push alert
  • Wipe Device → factory reset

Via ADB (what MDM does internally):

# Lock screen immediately
./android/adb-demo.sh lock

# Factory reset (demo only!)
./android/adb-demo.sh wipe

Without MDM: the device sits accessible until the attacker cracks the PIN. With MDM: locked within seconds, data wiped before physical access.

In the Headwind panel, go to the device list, click the device, show the action buttons. Click Lock — immediately see the emulator screen lock. Show the Wipe button but don't click it — explain what it does. Then show: ./android/adb-demo.sh lock for the command-line equivalent.

Demo 4 — iOS Configuration Profile iOS

Profile payload (mobileconfig):

<key>requireAlphanumeric</key> <true/>
<key>maxInactivity</key>      <integer>30</integer>
<key>maxFailedAttempts</key>  <integer>6</integer>

<!-- Restrictions -->

<key>allowInstallApp</key>                 <false/>
<key>allowUntrustedTLSPrompt</key>         <false/>
<key>forceEncryptedBackup</key>            <true/>
<key>allowOpenFromManagedToUnmanaged</key> <false/>

Install & enforce:

./ios/ios-sim-demo.sh show-profile

# Install on simulator
./ios/ios-sim-demo.sh install

Start by showing the show-profile output — it explains what each key does. Then run install. Open Simulator, go to Settings → General → VPN & Device Management. Run grant-revoke to show how MDM can control per-app permissions. Open Privacy to show what the user sees after the profile is applied.

App Permission Audit

Android — ADB audit:

./android/adb-demo.sh audit

# Or directly:
adb shell settings get global http_proxy
adb shell getprop ro.crypto.state
adb shell dumpsys device_policy
adb shell pm list packages

iOS — xcrun privacy control:

# Grant camera (simulate over-privileged app)
xcrun simctl privacy <UDID> grant \
camera com.apple.mobilesafari

# Revoke (MDM restriction enforcement)
xcrun simctl privacy <UDID> revoke \
camera com.apple.mobilesafari

# Reset all permissions
xcrun simctl privacy <UDID> reset all

MDM can also enforce app-level policies — block specific bundle IDs, require managed app configurations, and prevent data leakage between managed and unmanaged apps.

Run ./android/adb-demo.sh audit — show the output in the terminal. Then run ./ios/ios-sim-demo.sh grant-revoke — shows the same concept on iOS. Talk about "managed open-in" — iOS prevents corporate documents from being opened in personal apps like WhatsApp.

Key Takeaways

🔐 MDM shifts security from user responsibility to policy enforcement.
Users don't need to "remember" to turn on encryption — MDM won't let them turn it off.


🌐 Always-on VPN is the primary defence against network-layer attacks.
A rogue AP is useless if every connection is tunnelled before it hits the AP.


📱 Android and iOS take different architectural approaches to MDM.
iOS requires Apple's APNs push infrastructure. Android is more open but less consistent across OEMs.


👁️ Visibility is a security control.
You cannot protect what you cannot see. Compliance dashboards are threat detection tools.


🔓 MDM is defeated by physical access + no FDE, social engineering, and zero-days.
It is one layer. Combine with EDR, UEBA, and user training.

Wrap up in under 30 seconds. Leave time for questions. If asked about zero-days: MDM can enforce update policies to shrink the patch window, but a fresh zero-day beats MDM until a patch is deployed.
